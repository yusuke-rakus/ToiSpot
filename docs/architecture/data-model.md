# データモデル

[概要](../../README.md) · [文書一覧](../README.md)

保存先は `stores/{storeId}`。ローカル表示用に以下のスキーマを実装した。単一のZodスキーマを取得処理と保存処理で共有する。公開範囲、運用などの未決事項は後段の検討表と[決定管理](../decisions/README.md)に残す。

## 実装済みスキーマ

| フィールド               | 型・意味                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| `name`・`address`        | 空文字不可の文字列                                                                        |
| `location`               | `{ lat, lng }`。緯度−90〜90、経度−180〜180                                                |
| `geohash`                | geofire-commonで生成する位置の文字列。半径3kmの周辺検索に使用                             |
| `availability`           | `available`（利用可）・`unavailable`（利用不可）                                          |
| `stalls`                 | `{ male, female, shared }`。各値は非負整数またはnull                                      |
| `urinals`                | 男性用小便器数。非負整数またはnull                                                        |
| `notes`                  | 公開する備考の文字列                                                                      |
| `createdAt`・`updatedAt` | Timestamp。登録・編集はサーバー時刻。編集時は作成日時を保持し、再シードで両者を変更しない |
| `googlePlaceId`          | 必須のPlace ID。1〜512文字の英数字・`_`・`-`                                              |
| `isSample`               | falseのみ許可。未指定はfalseと解釈                                                        |

画面の `Store` 型はドキュメントIDを `id` に追加し、TimestampをISO日時文字列へ正規化する。検証ではDateとISO文字列も受け入れる。設備数の0は設備なし、nullは不明。合計は算出・表示しない。利用不可の設備数はすべてnullに限定し、利用可のときだけ記録・表示する。架空データはテスト専用とする。

登録編集には共有スキーマから導出した`StoreInput`を使う。geohash・サンプル識別・作成更新日時はフォーム入力に含めない。利用可の設備数は登録・編集フォームで0〜5から選択し、空欄は0へ変換する。利用不可では非表示の設備入力を検証せず、すべてnullへ変換する。

コンビニの種類は保存せず、地図のピンは店名から判定する。既存ドキュメントの旧`chainName`は読み取り時に無視し、登録済み店舗の次回保存時に削除する。

貸出状況は読み取り・入力・保存・Rulesを「利用可（available）」「利用不可（unavailable）」の2状態に統一する。新規登録では貸出状況を明示的に選ぶ。利用条件は備考に集約し、設備区分・最終確認日・利用条件専用フィールドと旧5状態の互換処理は持たない。旧`chainName`以外の未知のフィールドは読み取りスキーマで拒否する。Rulesは書き込み後のドキュメントに未知のフィールドがある場合に拒否する。

非公開の管理者設定は`_settings/admin`の`uid`に保持する。シードだけが変更し、公開店舗ドキュメントには認証情報を保存しない。

## 登録・修正申請

`storeRequests/{requestId}`へ公開前の申請を保存する。申請種別は`create`・`update`、状態は`pending`・`approved`・`rejected`とする。既存の`StoreInput`に対象店舗ID・Place ID・修正元の更新日時・申請日時・審査日時を加える。新規登録の店舗IDは申請IDで固定する。修正元の日時はFirestoreのTimestampをそのまま保存し、画面表示用ISO文字列から復元しない。

申請の作成だけはログイン不要とし、閲覧・承認・却下は管理者だけに許可する。承認時に店舗とPlace ID紐付けと申請状態を同一トランザクションで保存し、承認前は公開店舗を変更しない。修正元が更新済み、または新規申請先が登録済みの場合は上書きせず競合とする。申請本文は提出後に変更できない。処理済み申請は非公開で保持し、画面は申請中だけを表示する。

申請一覧は`status == pending`と`createdAt`の昇順で20件ずつ取得する。対応する複合インデックスを管理し、ベル件数は同じ条件の集計で取得する。

## 残る詳細設計の検討表

以下は当初の項目案と検討事項。上記のローカル用スキーマで定義した内容以外は引き続き検討対象とする。

| 分類   | 項目案                       | 要検討事項                             |
| ------ | ---------------------------- | -------------------------------------- |
| 識別   | 店舗ID                       | Firestoreの自動IDを候補とする          |
| 店舗   | 店名、住所                   | 必須項目、文字数制限                   |
| 位置   | 緯度、経度、geohash          | 座標の指定・修正方法と検証方法         |
| 貸出   | 利用可、利用不可             | 検索条件への反映                       |
| 備考   | 利用条件や補足を自由記述     | 公開範囲と入力案内                     |
| 個室   | 男性用、女性用、共用の個室数 | 「個室」の定義、設備なしと未確認の区別 |
| 小便器 | 男性用小便器数               | 有無と台数が部分的に分かる場合の表現   |
| 更新   | 作成日時、更新日時           | サーバー時刻での記録を候補とする       |

現時点の推奨は次のとおり。

- 設備数は非負整数とし、未確認を `null`、存在しないことを確認済みなら `0` とする。
- 個室数に小便器を含めず、合計の二重計上を避ける。
- 合計数を表示する場合、一部が不明なのに確定した合計として表示しない。
- 管理者のメールアドレスや認証情報を公開店舗ドキュメントに保存しない。
- 新規登録はPlaces APIで取得したコンビニに限定する。店名・住所を初期入力し、管理者がトイレ情報を追加する。座標はフォームに含めず、新規登録ではPlacesの位置、編集では保存済みの位置を保存時に引き継ぐ。

Places APIの検索結果全体は画面内に保持し、管理者が選択して保存した店舗だけをFirestoreに登録する。公開前のGoogle要件の確認は引き続き必要。

出典：[Maps JavaScript APIのポリシー](https://developers.google.com/maps/documentation/javascript/policies)、[Places APIのポリシー](https://developers.google.com/maps/documentation/places/web-service/policies)。

## Place IDの紐付け

`stores`の必須フィールド`googlePlaceId`と、`placeLinks/{placeId}`の`{ storeId: string }`を同一トランザクションで保存する。Place IDは1〜512文字の英数字・`_`・`-`で検証する。Place IDのない旧店舗と架空サンプルは[整理処理](../development/sample-data.md#旧データの整理)で削除し、スキーマ・Rulesでも登録を拒否する。

Place IDごとの紐付けは一意で、店舗側も別Place IDへの変更・解除を許可しない。同じ操作の再試行は重複作成しない。既存の手動登録店舗への紐付け機能は設けない。
