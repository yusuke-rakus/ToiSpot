管理者機能の承認計画により、Q-07の登録編集フォームと位置の引き継ぎ、Q-10のGoogle模擬認証・タブ内セッション・管理者交代を実装した。登録・編集を対象とし、削除は許可しない。当時は初期のメール・パスワード認証方針を変更したが、2026-11-07に以下の方針へ改定した。

## 周辺コンビニ表示の決定（2026-11-03）

承認計画に基づき、Places API（New）で半径3kmの近い最大20件を初期表示する。地図移動後は「この周辺を検索」で更新する。トイレ情報未登録だけを「データなし」とし、グレーのピンで表示する。登録済みの貸出状況「不明」と区別し、登録確認中・失敗では未登録と断定しない。

Googleの店舗情報は画面表示だけに使い、Place IDだけを紐付けのために保存する。管理者は独自に確認した店舗・トイレ情報を新規登録するか、既存の実店舗を手動で紐付ける。初期版の「Placesを使用しない」方針をこの追加要望で変更した。クラウド設定・公開・一括移行は含めない。

## Places店舗への登録統一（2026-11-03）

追加要望により、地図の任意地点へのピン設置・座標表示・コピーと、座標だけからの店舗登録を削除した。新規登録はPlaces APIで取得したコンビニを選ぶ方式に限定し、Place IDを必須とする。店名・住所・座標をフォームに引き継ぎ、管理者が保存した店舗だけをFirestoreへ登録する。店舗位置はフォームで変更できない。

従来のPlace IDのない店舗と架空サンプルはローカル整理コマンドで削除する。シードは管理者設定だけを扱い、店舗を再投入しない。旧店舗への手動紐付け機能は削除する。この決定を以前の地点選択・サンプル投入・Place IDのみ保存する方針より優先する。

## 現在のテストデータのシード化（2026-11-03）

追加要望により、Emulator内の万願寺周辺のテスト店舗7件を保存し、`pnpm seed`で店舗とPlace IDの紐付けの不足分を投入する。既存店舗・編集内容・日時は保持し、競合する紐付けは変更しない。店舗を投入しないという直前のシード方針を、この7件に限って変更する。店名・位置・Place IDはPlaces検索時の情報、トイレ情報は実地未確認の架空設定であり、備考にも明記する。旧来の架空店舗6件は再投入しない。接続先は従来どおりローカル18081番・`demo-toilet-map`に限定する。

## 本番公開・認証・Secrets管理（2026-11-04）

ユーザー確認により、本番でも管理者は1名とし、Firebase Authenticationに事前登録したGoogleアカウントだけログイン可能にする。未登録Googleアカウントの初回自動登録は禁止する。店舗の編集権限は現行の`_settings/admin.email`とSecurity Rulesで制限する。

APIキーなどの設定値とデプロイ用サービスアカウントJSONはGitHub Actions Secretsで管理する。MemoirAIのActionsを参考に、`main`へのpushで検証・ビルドし、Firestore Rules・インデックスの反映後にHostingを公開する構成例を[デプロイ手順](../operations/deployment.md)へ記載した。これは本番接続の実装、ワークフロー追加、クラウド設定、デプロイの実施を意味しない。Maps API有効化はユーザー申告で完了済みとし、そのほかのクラウド設定は要確認とする。

## トイレ情報の簡素化（2026-11-04）

利用不可では設備表示・入力を省き、保存時の設備数はすべてnullとする。利用可では共用・男性用・女性用の個室と男性用小便器をアイコン付きの2列で表示する。0は非表示、nullは不明、備考は空なら省く。設備区分・最終確認日・利用条件専用項目は型・フォーム・保存・Rulesから削除し、貸出状況を2状態に統一する。未リリースのため旧仕様の互換処理は保持せず、ローカルの既存データは一度だけ整理する。

## 本番接続とActionsの実装（2026-11-05）

本番Firebaseの閲覧・Google認証・登録編集に対応し、接続状態をEmulator・クラウド・無効に分離した。通常の開発はEmulatorを既定とし、e2eモードは設定に関係なく接続しない。既存の`pnpm build`・`pnpm check`を維持し、公開用の`pnpm build:production`で必須設定を検査する。

`main`へのpushで検証・本番ビルド・Firestore・Hostingの順に実行するActionsを追加した。テスト工程へ本番Secretsを渡さない。管理者は事前登録Googleユーザー1名とし、新規登録禁止とAuthユーザー登録はクラウド側の管理設定として維持する。DBスキーマ・Rulesの権限条件・シードの接続先は変更しない。クラウド設定・Secrets登録・push・実デプロイと実Google認証は実施していない。

## メール・パスワード認証への統一（2026-11-07）

ユーザー指定によりGoogle認証からFirebase標準のメール・パスワード認証へ変更する。任意IDはメールアドレス形式とする。本番とローカルで同じ画面・認証処理を使い、ローカルはEmulator専用アカウントと別パスワードを使う。管理者1名・一般利用者ログイン不要・新規登録禁止は維持する。

管理者設定は`{ email }`から`{ uid }`へ移行し、ブラウザとRulesでUIDと`password`プロバイダーを照合する。メール確認済み条件は外す。旧形式、別UID、Google認証は編集できない。旧設定・旧Googleプロバイダーは手順に沿って移行する。

本番はConsoleでユーザーを追加し、UIDを管理者設定へ登録する。ローカルは`ADMIN_EMAIL`・`ADMIN_PASSWORD`を指定してシードし、同じUIDを保ってパスワードを更新する。アプリ内に登録・再設定画面を追加しない。タブ内セッションと対象外アカウントのサインアウトを維持する。クラウド操作・デプロイ・commit・pushはこの作業に含めない。

## App Hostingへの公開方式変更（2026-11-07）

ユーザー指定により、公開先をFirebase App Hostingへ変更する。GitHub Actionsはテスト成功後に`GITHUB_SHA`を指定してロールアウトし、Firebase側のCloud Buildで本番ビルドする。バックエンドの自動ロールアウトは無効にし、検証前の公開を防ぐ。Firebase・Mapsの`VITE_*`6項目は既存のGitHub Actions Secretsを正としてSecret Managerへ同期し、YAMLには参照だけを記載する。検索フラグ・上限はGit管理する。ActionsにはプロジェクトID・バックエンドID・デプロイ認証も設定する。Vite SPAはカスタムビルドとNode.js配信サーバーを使う。Blazeプラン・GitHub接続済みバックエンド・IAMの準備が必要で、クラウド変更・実デプロイは実施していない。手順は[デプロイ手順](../operations/deployment.md)を参照する。
